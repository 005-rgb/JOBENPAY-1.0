PRD 1.8 — JobenPay Policy Language (JPL) Specification
Standar Terbuka untuk Kebijakan Kontrol Agen AI yang Dapat Diaudit
Versi: 1.0 · Status: Standard Specification, Implementation-ready, Zero-Hallucination
Tanggal: 7 November 2026
Basis: PRD 1.2 §10.1 (policy schema) + PRD 1.3 (universal transaction) + PRD 1.6 (DIP)
Prinsip: Setiap field, operator, dan test eksplisit. AI builder tidak perlu menebak. Tidak ada "disiratkan".
Filosofi: Dokumen ini ditulis untuk dibaca 10 tahun dari sekarang, ketika model AI sudah berganti berkali-kali, tetapi aturan bisnis tetap sama.

0. ATURAN EMAS (NON-NEGOTIABLE)
JPL adalah bahasa deklaratif, bukan bahasa pemrograman. Tidak ada loop, tidak ada function, tidak ada side effect. Hanya aturan yang dapat dievaluasi secara deterministik.

JPL tidak bergantung pada model AI. Policy yang ditulis dalam JPL dapat dievaluasi oleh interpreter mana pun, tanpa memanggil LLM.

JPL memiliki compiler dan verifier referensi. Setiap implementasi JPL wajib lulus conformance test suite.

JPL backward compatible minimal 10 tahun. Versi lama tetap dapat dievaluasi oleh interpreter baru.

JPL deterministik. Evaluasi policy yang sama dengan input yang sama selalu menghasilkan output yang sama.

JPL fail-closed. Jika evaluasi tidak dapat diselesaikan (data hilang, tipe salah), hasilnya DENY — bukan PERMIT.

Coverage 100% untuk jpl_compiler.js, jpl_evaluator.js, jpl_verifier.js. CI gagal jika < 100%.

Setiap test case memiliki assertion eksplisit (§9). Tidak ada "test bahwa X berfungsi".

1. RINGKASAN DAN FILOSOFI
1.1 Masalah yang Diselesaikan
Saat ini, setiap platform kontrol agen AI memiliki bahasa policy sendiri:

JOBENPAY 1.2 menggunakan JSON Schema dengan field perTransactionCapMinor, allowedActions, dll.

Sardis menggunakan YAML dengan spend_limits, merchant_rules, dll.

Mercury menggunakan UI form dengan checkbox.

Stripe menggunakan API call dengan parameter.

Akibatnya:

Tidak ada interoperabilitas. Policy yang ditulis untuk JOBENPAY tidak dapat dievaluasi oleh sistem lain.

Tidak ada auditability. Regulator tidak dapat memverifikasi bahwa policy yang diklaim benar-benar dievaluasi.

Tidak ada portabilitas. Jika perusahaan pindah vendor, policy harus ditulis ulang.

Tidak ada standar. Setiap vendor mendefinisikan semantiknya sendiri, dan tidak ada cara untuk membandingkan.

1.2 Solusi: JobenPay Policy Language (JPL)
JPL adalah bahasa deklaratif terbuka untuk mengekspresikan kebijakan kontrol agen AI. JPL mendefinisikan:

Syntax — bagaimana policy ditulis (JSON-based).

Semantics — bagaimana policy dievaluasi (deterministik, fail-closed).

Compiler — bagaimana policy dikompilasi menjadi executable rules.

Evaluator — bagaimana policy dievaluasi terhadap input.

Verifier — bagaimana policy diverifikasi (hash, signature).

Conformance Test Suite — bagaimana implementasi diverifikasi.

1.3 Filosofi
"Kebijakan harus dapat dibaca oleh manusia, dievaluasi oleh mesin, dan diverifikasi oleh siapa pun. Jika tidak, itu bukan kebijakan — itu kotak hitam."

JPL dirancang untuk bertahan 10 tahun, karena:

Tidak bergantung pada model AI.

Tidak bergantung pada vendor.

Tidak bergantung pada teknologi pembayaran.

Hanya bergantung pada logika dan matematika.

2.2 Yang Tidak Termasuk
Bukan bahasa pemrograman (tidak ada loop, function, side effect).

Bukan pengganti AI intent check (PRD 1.2 §9.5 Tahap C); JPL adalah lapisan deterministik.

Bukan jaminan bahwa policy "benar" secara moral; JPL hanya memverifikasi evaluasi yang konsisten.

Bukan sistem manajemen policy (tidak ada UI, database, atau workflow).

3. JPL SYNTAX SPECIFICATION
3.1 Struktur Dasar

  "signature": { /* ... */ }

3.4 Field Path Resolution
Field path menggunakan dot notation:

request.category → request.category

request.amount_minor → request.amount_minor

mandate.policy.budget.limit_minor → mandate.policy.budget.limit_minor

agent.status → agent.status

counterparty.category → counterparty.category

Aturan:

Jika field tidak ada di input, evaluasi → false (kecuali operator exists/not_exists).

Jika field adalah null, evaluasi → false (kecuali operator exists/not_exists).

Jika field path invalid (tidak cocok dengan regex), compiler → error.

3.5 Prioritas dan Evaluasi
Aturan evaluasi:

Semua rule diurutkan berdasarkan priority (ascending: 1 = tertinggi).

Rule pertama yang semua kondisi-nya true → outcome-nya digunakan.

Jika tidak ada rule yang cocok → default_outcome.

Explicit deny precedence: Jika ada rule dengan outcome DENY yang cocok, hasilnya DENY — bahkan jika rule lain dengan priority lebih tinggi menghasilkan PERMIT. (Ini adalah aturan keamanan.)

Contoh:

json
{
  "rules": [
    { "rule_id": "rule_deny_blocked_vendor", "priority": 1, "conditions": [...], "outcome": "DENY" },
    { "rule_id": "rule_permit_trusted_vendor", "priority": 2, "conditions": [...], "outcome": "PERMIT" }
  ],
  "default_outcome": "DENY"
}
Jika rule_deny_blocked_vendor cocok → DENY. Jika tidak, cek rule_permit_trusted_vendor → PERMIT. Jika tidak ada yang cocok → DENY.

4. JPL SEMANTICS SPECIFICATION
4.1 Evaluasi Deterministik
Fungsi: evaluate(policy, input) → outcome

Algoritma:

text
1. Validasi policy terhadap JSON Schema. Jika invalid → error.
2. Urutkan rules berdasarkan priority (ascending).
3. Untuk setiap rule (dari priority terendah):
   a. Evaluasi semua conditions dengan AND.
   b. Jika semua conditions true → rule cocok.
   c. Jika rule.outcome == "DENY" → return DENY (explicit deny precedence).
   d. Jika rule cocok tetapi outcome != "DENY" → simpan sebagai kandidat.
4. Jika ada kandidat (non-DENY) → return kandidat pertama.
5. Jika tidak ada kandidat → return default_outcome.
Aturan fail-closed:

Jika input tidak memiliki field yang dirujuk → kondisi = false.

Jika tipe data tidak cocok (misalnya gt pada string) → kondisi = false.

Jika evaluasi error (misalnya regex invalid) → return DENY dengan reason EVALUATION_ERROR.

4.2 Explicit Deny Precedence
Aturan ini adalah keamanan fundamental:

Jika ada rule dengan outcome DENY yang cocok, hasilnya selalu DENY — bahkan jika ada rule lain dengan priority lebih tinggi yang menghasilkan PERMIT.

Rasional: Dalam sistem keamanan, "deny" harus selalu menang. Jika ada keraguan, tolak.

Contoh:

json
{
  "rules": [
    { "rule_id": "rule_permit", "priority": 1, "conditions": [...], "outcome": "PERMIT" },
    { "rule_id": "rule_deny", "priority": 2, "conditions": [...], "outcome": "DENY" }
  ]
}
Jika keduanya cocok → DENY (karena rule_deny cocok, dan explicit deny precedence berlaku).

4.3 Evaluasi Kondisi
Fungsi: evaluateCondition(condition, input) → boolean

Algoritma:

text
1. Resolve field path di input.
2. Jika field tidak ada dan operator bukan exists/not_exists → return false.
3. Evaluasi operator sesuai tabel §3.3.
4. Jika operator error (misalnya regex invalid) → return false (fail-closed).
5. Return hasil.
4.4 Versioning
Aturan:

Setiap policy memiliki jpl_version.

Interpreter wajib mendukung minimal 10 tahun versi lama.

Jika interpreter tidak mendukung versi → error UNSUPPORTED_JPL_VERSION.

Perubahan semantik (misalnya operator baru) → versi minor (1.1).

Perubahan struktur (misalnya field baru) → versi minor (1.1).

Perubahan breaking (misalnya menghapus operator) → versi major (2.0).

5. JPL COMPILER
5.1 Tujuan
Compiler mengubah policy JSON menjadi executable rules yang dapat dievaluasi dengan cepat (O(1) per rule).

5.2 Prosedur
text
1. Validasi policy terhadap JSON Schema.
2. Verifikasi signature (jika ada).
3. Kompilasi setiap rule:
   a. Parse field path menjadi accessor function.
   b. Compile operator menjadi evaluator function.
   c. Simpan sebagai closure.
4. Urutkan rules berdasarkan priority.
5. Return compiled policy object.
5.3 Output Compiler
javascript
{
  policy_id: "pol_01HX...",
  policy_hash: "sha256:...",
  rules: [
    {
      rule_id: "rule_deny_blocked_vendor",
      priority: 1,
      outcome: "DENY",
      outcome_params: { reason_code: "PAYEE_BLOCKED" },
      evaluate: (input) => { /* compiled closure */ }
    },
    // ...
  ],
  default_outcome: "DENY",
  evaluate: (input) => { /* main evaluator */ }
}
5.4 Idempotensi
Compiler harus deterministik: policy yang sama → compiled policy yang sama (kecuali closure function, yang tidak dapat dibandingkan).

Test: test_compiler_deterministic — compile policy 2x → output hash sama.

6. JPL EVALUATOR
6.1 API
javascript
import { compile, evaluate } from '@jobenpay/jpl';

const policy = JSON.parse(fs.readFileSync('policy.json', 'utf8'));
const compiled = compile(policy);

const input = {
  request: { category: 'PAYOUT', amount_minor: 45000, currency: 'USD' },
  counterparty: { trust: 'TRUSTED', category: 'electronics' },
  agent: { status: 'ACTIVE' },
  org: { frozen: false }
};

const result = evaluate(compiled, input);
// { outcome: 'REQUIRE_APPROVAL', rule_id: 'rule_require_approval_amount', reason_code: 'AMOUNT_REQUIRES_APPROVAL' }
6.2 Output Evaluator
javascript
{
  outcome: "PERMIT" | "DENY" | "REQUIRE_APPROVAL" | "ESCALATE",
  rule_id: string | null,
  reason_code: string | null,
  outcome_params: object,
  evaluated_at: string (ISO-8601)
}

7. JPL VERIFIER
7.1 Tujuan
Verifier memverifikasi bahwa policy:

Valid terhadap JSON Schema.

Memiliki signature yang valid.

Hash-nya cocok dengan yang tercatat di ledger.

Tidak dimanipulasi.

7.2 API
javascript
import { verify } from '@jobenpay/jpl';

const result = verify(policy, { publicKey, expectedHash });
// { valid: true, checks: [...] }
7.3 Prosedur
text
1. Validasi policy terhadap JSON Schema.
2. Hitung hash = SHA-256(canonicalize(policy tanpa signature)).
3. Jika expectedHash diberikan, bandingkan.
4. Verifikasi signature dengan publicKey.
5. Return { valid, checks }.

14. LAMPIRAN: CONTOH PENGGUNAAN
A.1 Evaluasi Policy
javascript
import { compile, evaluate } from '@jobenpay/jpl';

const policy = {
  jpl_version: "1.0",
  policy_id: "pol_01HX...",
  policy_name: "Standard Payout Policy",
  rules: [
    {
      rule_id: "rule_deny_blocked",
      priority: 1,
      conditions: [{ field: "counterparty.trust", operator: "eq", value: "BLOCKED" }],
      outcome: "DENY",
      outcome_params: { reason_code: "PAYEE_BLOCKED" }
    },
    {
      rule_id: "rule_permit_trusted",
      priority: 10,
      conditions: [
        { field: "counterparty.trust", operator: "eq", value: "TRUSTED" },
        { field: "request.amount_minor", operator: "lt", value: 20000 }
      ],
      outcome: "PERMIT",
      outcome_params: { reason_code: "PAYEE_TRUSTED" }
    }
  ],
  default_outcome: "DENY"
};

const compiled = compile(policy);

const input = {
  request: { amount_minor: 15000 },
  counterparty: { trust: "TRUSTED" }
};

const result = evaluate(compiled, input);
// { outcome: "PERMIT", rule_id: "rule_permit_trusted", reason_code: "PAYEE_TRUSTED" }

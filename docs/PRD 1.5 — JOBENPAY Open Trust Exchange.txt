PRD 1.5 — JOBENPAY Open Trust Exchange
Protokol Terbuka untuk Verifikasi Otorisasi Agen Lintas Platform (Presisi Tinggi, Zero-Hallucination)
Versi: 1.0 · Status: Implementation-ready specification
Tanggal: 7 November 2026
Basis: PRD 1.2 (Sandbox Gatekeeper) + PRD 1.3 (Universal Transaction Engine) + PRD 1.4 (Trust Infrastructure)
Prinsip: Setiap field, endpoint, state, dan test eksplisit. AI builder tidak perlu menebak. Tidak ada "disiratkan".

0. ATURAN EMAS (NON-NEGOTIABLE)
Protokol adalah spesifikasi publik. Setiap perubahan pada format SAR, endpoint handshake, atau revocation feed wajib memiliki versi (protocol_version) dan backward compatible minimal 12 bulan.

Setiap endpoint memiliki request/response schema eksplisit (§5). Tidak ada field opsional yang tidak didokumentasikan.

Setiap test case memiliki assertion eksplisit (§11). Tidak ada "test bahwa X berfungsi".

Coverage 100% untuk modul protocol_service.js, handshake_service.js, dan verify_service.js. CI gagal jika < 100%.

Fail-closed: jika verifikasi tidak dapat diselesaikan (registry down, revocation feed tidak tersedia), hasilnya INDETERMINATE — bukan VERIFIED.

Tidak ada PII di payload protokol. Hanya hash, ID, enum, timestamp, dan tanda tangan.

Kompatibel dengan AP2: format SAR dapat dipetakan ke AP2 mandate (jika AP2 tersedia), tetapi tidak bergantung padanya.

1. RINGKASAN DAN FILOSOFI
1.1 Masalah yang Diselesaikan
PRD 1.2 dan 1.3 membangun kontrol internal yang sangat kuat: mandat, gerbang deterministik, ledger berantai-hash. PRD 1.4 menambahkan verifikasi lintas organisasi melalui SAR dan Issuer Registry.

Tetapi ada celah fundamental yang belum dijawab oleh siapa pun — termasuk AP2, PayPal, dan seluruh ekosistem pembayaran AI:

Ketika agen dari Perusahaan A mengirim pembayaran ke Vendor B, bagaimana Vendor B tahu bahwa pembayaran itu sah — tanpa harus memakai sistem yang sama dengan Perusahaan A?

Saat ini, jawabannya adalah "saling percaya secara manual" (kontrak, email) atau "memakai platform yang sama" (lock-in). Tidak ada standar terbuka yang memungkinkan verifikasi lintas platform tanpa ketergantungan pada satu vendor.

1.2 Solusi: Open Trust Exchange
JOBENPAY Open Trust Exchange adalah protokol terbuka yang mendefinisikan:

Format SAR (Signed Authorization Receipt) — artefak kriptografis yang membuktikan otorisasi transaksi.

Endpoint verifikasi publik — siapa pun dapat memverifikasi SAR tanpa akun.

Trust Handshake — pertukaran kriptografis singkat sebelum transaksi, memungkinkan vendor meminta bukti otorisasi terlebih dahulu.

Revocation Feed — feed publik yang memungkinkan verifier mengetahui pencabutan secara real-time.

Spesifikasi protokol — dokumen publik yang memungkinkan platform lain (Stripe, bank, pesaing) mengimplementasikan protokol yang sama.

1.3 Filosofi
"Kepercayaan tidak boleh menjadi milik satu perusahaan. Jika JOBENPAY ingin dipercaya oleh ekosistem, JOBENPAY harus membuat kepercayaan itu dapat diverifikasi oleh siapa pun — termasuk pesaingnya."

Ini adalah lompatan dari "produk" menjadi "standar". JOBENPAY tidak lagi bersaing dengan platform lain; JOBENPAY menjadi lapisan netral yang menghubungkan semuanya.

3.2 Canonicalization
Aturan: SAR ditandatangani atas canonical JSON (RFC 8785 — JSON Canonicalization Scheme).

Kunci diurutkan leksikografis.

Tanpa spasi.

Angka direpresentasikan sebagai string (untuk amount_minor).

undefined dibuang.

Unicode dinormalisasi NFC.

Implementasi referensi: canonicalize(sar) di shared/canonical.js (sudah ada di PRD 1.2 D4).

3.3 Signing
Algoritma: Ed25519 (RFC 8032).

Prosedur:

Ambil SAR tanpa field signature.

Canonicalize → string C.

Hitung hash = SHA-256(C).

Tanda tangani hash dengan private key issuer → sig.

Tambahkan signature: { alg: "Ed25519", kid, sig: base64(sig) }.

Verifikasi:

Ambil SAR, hapus signature.

Canonicalize → C.

Hitung hash = SHA-256(C).

Verifikasi sig terhadap hash dengan public key issuer (dari registry).

Jika valid → signature_valid: true.

4. SKEMA DATA
4.1 Tabel Baru
sql
-- 4.1.1 Protocol Versions (untuk versioning)
CREATE TABLE protocol_versions (
  version_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  protocol_version TEXT NOT NULL UNIQUE,
  schema_json JSONB NOT NULL,
  released_at TIMESTAMPTZ NOT NULL,
  deprecated_at TIMESTAMPTZ,
  status TEXT NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE','DEPRECATED','RETIRED')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_protocol_versions_status ON protocol_versions(status);

-- 4.1.2 Public Proofs (link publik untuk verifikasi)
CREATE TABLE public_proofs (
  proof_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  sar_id TEXT NOT NULL,
  org_id UUID NOT NULL REFERENCES organizations(org_id),
  sar_json JSONB NOT NULL,
  proof_url TEXT NOT NULL UNIQUE,
  created_by UUID NOT NULL REFERENCES users(user_id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at TIMESTAMPTZ NOT NULL,
  access_count INT NOT NULL DEFAULT 0,
  revoked_at TIMESTAMPTZ,
  CHECK (expires_at > created_at)
);

CREATE INDEX idx_public_proofs_sar ON public_proofs(sar_id);
CREATE INDEX idx_public_proofs_org ON public_proofs(org_id);
CREATE INDEX idx_public_proofs_url ON public_proofs(proof_url);
CREATE INDEX idx_public_proofs_expires ON public_proofs(expires_at) WHERE revoked_at IS NULL;

-- 4.1.3 Trust Handshakes (pra-transaksi)
CREATE TABLE trust_handshakes (
  handshake_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  requester_org_id UUID NOT NULL REFERENCES organizations(org_id),
  target_org_id UUID NOT NULL REFERENCES organizations(org_id),
  agent_id UUID NOT NULL,
  request_intent JSONB NOT NULL,  -- {category, amount_minor, currency, payee_hmac}
  handshake_nonce TEXT NOT NULL UNIQUE,
  status TEXT NOT NULL DEFAULT 'PENDING' CHECK (status IN (
    'PENDING','VERIFIED','DENIED','EXPIRED','INDETERMINATE'
  )),
  response_json JSONB,
  issued_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at TIMESTAMPTZ NOT NULL,
  responded_at TIMESTAMPTZ,
  CHECK (expires_at > issued_at)
);

CREATE INDEX idx_trust_handshakes_requester ON trust_handshakes(requester_org_id);
CREATE INDEX idx_trust_handshakes_target ON trust_handshakes(target_org_id);
CREATE INDEX idx_trust_handshakes_nonce ON trust_handshakes(handshake_nonce);
CREATE INDEX idx_trust_handshakes_status ON trust_handshakes(status);

-- 4.1.4 Conformance Vectors (untuk implementasi pihak ketiga)
CREATE TABLE conformance_vectors (
  vector_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  vector_name TEXT NOT NULL UNIQUE,
  sar_json JSONB NOT NULL,
  expected_result TEXT NOT NULL CHECK (expected_result IN ('VALID','INVALID','INDETERMINATE')),
  expected_reason TEXT,
  category TEXT NOT NULL CHECK (category IN (
    'SCHEMA','SIGNATURE','REVOCATION','HASH','EXPIRY','COMPOSITION'
  )),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_conformance_vectors_category ON conformance_vectors(category);

-- 4.1.5 Partner Systems (untuk demo lintas platform)
CREATE TABLE partner_systems (
  partner_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  partner_name TEXT NOT NULL,
  partner_type TEXT NOT NULL CHECK (partner_type IN ('SIMULATED','REAL')),
  base_url TEXT NOT NULL,
  public_key_jwk JSONB,
  status TEXT NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE','SUSPENDED','REVOKED')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

    "alg": "Ed25519",

  "handshake_id": "hs_01HX...",
  "status": "VERIFIED",

6. STATE MACHINE
6.1 Trust Handshake State Machine
text
PENDING → VERIFIED
PENDING → DENIED
PENDING → INDETERMINATE
PENDING → EXPIRED (jika expires_at < now())
Transisi legal:

Dari	Ke	Trigger
PENDING	VERIFIED	Target respond dengan verdict VERIFIED + SAR valid
PENDING	DENIED	Target respond dengan verdict DENIED
PENDING	INDETERMINATE	Target respond dengan verdict INDETERMINATE
PENDING	EXPIRED	Job expire_handshakes (setiap 1 menit)
Aturan:

Setelah VERIFIED/DENIED/INDETERMINATE, handshake tidak dapat diubah.

EXPIRED hanya terjadi jika tidak ada respons dalam 5 menit.

6.2 Public Proof State Machine
text
ACTIVE → REVOKED
ACTIVE → EXPIRED (jika expires_at < now())
Transisi legal:

Dari	Ke	Trigger
ACTIVE	REVOKED	OWNER/ADMIN klik "Revoke proof"

16. LAMPIRAN: CONTOH ALUR LENGKAP
16.1 Alur Vendor Menerima Pembayaran
text
1. Agen (Perusahaan A) mengusulkan pembayaran ke Vendor B.
2. JOBENPAY (Perusahaan A) mengevaluasi → AUTO_APPROVE.
3. JOBENPAY mengeksekusi ke PayPal Sandbox → EXECUTED.
4. JOBENPAY menerbitkan SAR (v1.0).
5. JOBENPAY membuat public proof: GET /proof/abc123 → link.
6. JOBENPAY mengirim link ke Vendor B (via email/API).
7. Vendor B membuka link → halaman verifikasi → VERIFIED.
8. Vendor B memproses pesanan.
9. Vendor B dapat mengunduh SAR + bukti verifikasi untuk audit.
16.2 Alur Trust Handshake (Pra-Transaksi)
text
1. Agen (Perusahaan A) ingin mengirim pembayaran ke Vendor B.
2. Vendor B memanggil POST /v1/handshake/initiate dengan request_intent.
3. JOBENPAY merespons dengan handshake_nonce + expires_at.
4. Vendor B mengirim handshake_nonce ke JOBENPAY (via UI/API).
5. JOBENPAY (Perusahaan A) memverifikasi intent → menghasilkan SAR.
6. JOBENPAY memanggil POST /v1/handshake/{id}/respond dengan verdict VERIFIED + SAR.
7. Vendor B menerima respons → status VERIFIED.
8. Vendor B memproses pesanan.
9. Transaksi aktual terjadi (payout).
16.3 Alur Demo Lintas Platform (untuk Video)
text
1. Agen A (JOBENPAY) mengirim pembayaran ke Vendor C.
2. Vendor C memverifikasi via Open Trust Exchange → VERIFIED.
